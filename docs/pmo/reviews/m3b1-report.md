### The policy's rules (PAY-02)
1. Sample mode is `.demo`. 2. Only a transaction that is verified, for this role's product (exact ID: the parent ID also ends in `.annual`), not upgraded, and purchased counts; anything else is ignored as if absent, so **unverified input never entitles** and **a parent plan never unlocks the student role, nor the reverse**. 3. A revocation (refund) lapses at once. 4. A billing grace period entitles to its end. 5. `expired`, `inBillingRetryPeriod` and `revoked` settle it at the expiry; `subscribed`, `inGracePeriod` or an unknown state (offline) keep access 3 days past the expiry, then fail closed. 6. Clock skew: time is the later of `now` and the newest App Store signed date counted. 7. The latest end wins; with none entitling, `.lapsed` once the first sync has succeeded, else `.preview` (a lapsed student who signs in again gets the free first sync, pricing R9).

## 2. Decisions and deviations

- **D1. The gate hook is `RefreshCoordinator`, not `AppModel`.** Every refresh trigger reaches the network only through `RefreshCoordinator.run(trigger:)`: the launch and pull-to-refresh (`HomeModel` → `AccountHomeSource`), the background task (`AccountRuntime.backgroundRefresh`), the "Refresh Tally" intent (`RefreshIntentBridge`, M3-D's file, untouched) and the first sync. `AppModel` sees none of the background or intent paths. The coordinator is also where the glance is written, so the mirror rides the same `rewriteGlance` path as "Show Grades in Widgets", and it is Linux-testable.
- **D2. Files outside the list, each small and additive** (no parallel stream owns them): `TallyStore/SnapshotStore.swift` (the glance is written only there, `SnapshotStore.swift:67-91,139-166`: `commit`/`rewriteGlance` take `entitledUntil`, the self-heal carries it forward); `Account/AccountEnvironment.swift` (an `entitlement` port, ungated by default) and `Account/AccountSessionFactory.swift` (one argument: every coordinator gets the gate); `apps/TallyiOS/Tally/AppEnvironment.swift` (the composition root builds the gate, the engine and its adapters; `entitlementSource`, §2 D12). Tests of those files: `GlanceProjectionTests` (the key-set guard, deliberately), new suites elsewhere.
- **D3. Background refresh was never requested.** `.backgroundTask(.appRefresh)` was registered but nothing ever submitted a `BGAppRefreshTaskRequest` (perf-app-runtime.md §2.4 B6, planned, not built), so iOS never ran it. PAY-07 needs a schedule to withdraw, so `BackgroundRefreshScheduler` now requests it (60 min, `TallyConfig.bgEarliestBegin`) at the launch's verification, when the scene enters the background and after each background run, while the gate allows it. With enforcement off this is new behaviour on devices (UNVERIFIED: the simulator never runs background tasks).
- **D4. The 3-day grace applies only where StoreKit cannot settle it** (offline, `subscribed` over a stale transaction, grace period without a verified end): a verified expiry, a billing retry or a refund lapses at once. A verified lapse also clears the record's expiry, so the widgets lock at once instead of three days later.
- **D5. `firstSyncSucceeded`** distinguishes `.lapsed` from `.preview`, and the gate lets a run with no committed snapshot through whatever the state (the free first sync).
- **D6. Ownership:** `.purchased` entitles; `.familyShared` never does (Family Sharing is off); anything else (`.assigned`, an organization's seat) maps to `.other` and never entitles. The StoreKit symbol `.assigned` is not referenced: its first SDK is UNVERIFIED and CI builds with Xcode 26.6 (O1).
- **D7. The engine never resolves the account itself.** `AppModel.attach` hands it the coordinator (weakly held) and sign-out detaches it, so the launch's snapshot decode is not moved and sign-out's release is not delayed.
- **D8. Renewal and expiry in StoreKit Testing run at one second a day** (`SKTestSession.TimeRate` raw value 6, as RevenueCat's suites do; the brief asks for an accelerated renewal). The trial renews, or with auto-renewal off expires, by itself about 30 s after the purchase; the session's forced renewal and expiry are still asked for and only bring that forward. The first session chose the forced renewal alone, which had not reached StoreKit's view when the engine read it (run 36956766992, §4.2).
- **D9. Only an entitlement requests the background refresh, and only a verified lapse withdraws it;** a preview (no transaction visible: never subscribed, or StoreKit not readable yet, as in a background launch before the first unlock) leaves it alone. A request a preview leaves behind runs into the coordinator's own gate.
- **D10. An account attached after a lapse gets one reminders pass at the attach.** At launch the pipeline's first pass can run with the Keychain record's answer before StoreKit's lapse arrives; the engine only sees changes while attached, so the attach withdraws what that pass left.
- **D11. `finish()` covers only what the granting verification read**, so a transaction that arrives between a verification's read and its finish step waits for the verification that grants it.
- **D12. StoreKit Testing: what was wrong, and where the suite runs.** Run 36943065198 served Tally Annual to no scenario on iOS 26.5, and the first session blamed the iOS 26.3-26.5 simulators. That came from one public project (`stanlsv/sayboard`), whose own `.storekit` is a hand-trimmed version 1.0 file with empty settings and whose test is disabled on every iOS 26 simulator; RevenueCat's StoreKit suites pass on iOS 26.3.1 (`RevenueCat/purchases-ios` commit `652c1fae9`, 2026-09-21). Four faults were fixed, none by weakening a test. The runs show the first and fourth faults, and the fourth's fix passed in PR run 36961581422 (all 7 scenarios on the 26.2 floor); whether the second and third mattered is not proven either way (iOS 26.5 serves nothing with both fixed, 26.2 serves our file with both fixed, and no run had 26.2 without them):
  1. **The circular trait** (run 36946834779's build failure): the suite's `.enabled(if:)` read a static member of the suite itself. The condition now lives in its own type, `StoreKitProbe`.
  2. **The file's shape** (`05effc5`): against six Xcode-saved version 4 files (Brave, KeePassium, RevenueCat, Pocket Casts, Proton Pass, flutter/packages), `Products.storekit` lacked the nine `_storeKitErrors` settings and gave its free trial a `numberOfPeriods`; both now match, and no other key differs.
  3. **The test host's first StoreKit connection** (`10e91d0`): a process's first StoreKit connection decides its environment, and one made before the `SKTestSession` stays in Sandbox, so product requests come back empty (RevenueCat's `StoreKitConfigTestCase`). The app's own engine connected at `TallyApp.init`, before any test. In a Debug process that hosts TallyAppTests (`XCTestConfigurationFilePath` set, never in an app a UI test launches) it now gets `NoEntitlementSource`; Release always gets StoreKit. `StoreKitTestHostTests` pins it, and it passed in run 36954768450.
  4. **The scenarios waited for the wrong view** (`90afba5`): they waited until the test session showed an action, then ran their one foreground 0.3 s later, before StoreKit's own view (the one the engine reads) had it (run 36956766992, §4.2). Each now waits for `Transaction.latest(for:)` to show the change, as a public suite does after the same actions (`AChep/keyguard-app`, `StoreKitBillingTests`), then runs the one foreground; renewal and expiry run at one second a day (D8).

  **Where it runs.** Instead of a version range, a simulator asks StoreKit Testing for the one subscription of a control configuration (`TallyAppTests/StoreKitProbe.storekit`: plain, Xcode's shape, nothing shared with `Products.storekit`), for up to 20 s (`7e4d9e7`: Swift Testing evaluates the condition while it plans the run, moments after launch, and StoreKit Testing can answer with an empty list for a few seconds after a session is set up). The suite is skipped, with that reason, only when the control is never served; a runtime that serves the control but not our two products fails `productsLoad`, which prints the served IDs. Each scenario's session also waits up to 10 s for both products before it starts. **On CI the suite runs on the 26.2 floor only:** in run 36956766992, iOS 26.5 never served the control even with the 20 s patience, so the suite was skipped; the 26.2 floor served it and both of `Products.storekit`'s products as configured (`productsLoad` passed). The suite therefore runs in `ios-build`'s floor step (required) and is skipped in `ios-build`'s 26.5 run, `ios-tsan` and `ios-asan`. Why 26.5 serves nothing is not established (O8).
