## Step 2 — SEC1-02 variant: the one-time "couldn't confirm the revoke" notice

`packages/TallyCore/Sources/TallySync/SignOutUseCase.swift`: `signOut(...)` now returns
`@discardableResult Bool` — `true` only when a credential existed and the revoke did not end in a
2xx (offline, a transport error, or any other status, even after the one refresh SEC-FIX-1 added).
`false` both on a successful revoke and when there was nothing to revoke, so a repeat sign-out can
never resurface the notice. The local purge is unconditional either way (unchanged).

`packages/TallyAppleKit/Sources/TallyFeatures/Account/AccountSignOut.swift`: `purge(...)` forwards
that `Bool` (also `@discardableResult`); the early "no store root" branch returns `false` (nothing
was attempted — a build misconfiguration, not "offline").

`packages/TallyAppleKit/Sources/TallyFeatures/Shell/AppModel.swift`: new `showsSignOutRevokeNotice`
(reset at the top of `signOut()`, set from the teardown task's `AccountSignOut.purge` result) and
`dismissSignOutRevokeNotice()`. Deliberately session-only, not persisted — the same pattern as the
existing `isSchoolNoticeDismissed`/`dismissSchoolRevokedNotice()` (PAY-10): a courtesy notice, not
a security control, so losing it to an early relaunch is an acceptable, proportionate gap for a
Low-severity optional variant.

`packages/TallyAppleKit/Sources/TallyFeatures/Onboarding/WelcomeFlowView.swift`: a plain
`.alert(title, isPresented:) { Button(ok, role: .cancel) {} } message: { Text(message) }`, the
same pattern already used for the sample-feed alert (`CalendarScreen.swift`/`SettingsView.swift`).
Placed on `WelcomeFlowView` because that is "the post-sign-out surface the report suggests" — the
SEC-1 report's own SEC1-08 narrative says, verbatim, "the credential and the `accounts.json`
record are removed, and the UI goes to Welcome" — and `signOut()` already routes there before the
teardown task (and this notice) even starts.

Copy: 3 new keys under `L10n.Welcome` (`welcome.revokeNotice.{title,message,ok}`), en +
es `needs_review`, added to `Localizable.xcstrings` with matching `defaultValue`s. No exploit
detail; names the ~2-hour Canvas access-token lifetime from `docs/pmo/reviews/security.md` §3.2
item 9.4 (already a committed, public doc) and points the student at Canvas's own Approved
Integrations page.

Test: `SignOutUseCaseTests.swift` — new `signOutReportsAFailedRevokeForTheOptionalNotice` (a 500
revoke reports `true`; a second, credential-less call reports `false`); added assertions to the
two existing SEC1-02 tests that a successful revoke reports `false`. `SignOutTests.swift`
(TallyAppTests, `#if DEBUG`, iOS-hosted) — new `showsTheRevokeNoticeOnlyWhenRevocationFailed`
(`RecordingTransport.revokeStatus = 500`, asserts the notice appears and clears on dismiss) and
`noNoticeWhenRevocationSucceeds`. `AccountLifecycleTestSupport.swift`'s shared `RecordingTransport`
gained a `revokeStatus` var (default 200, so every other suite is unaffected) — a small, additive
change to a file shared with the other work package in this brief's lane.

## Step 3 — SEC1-10 variant: a neutral spoken answer while App Lock is on

`packages/TallyAppleKit/Sources/TallyGlance/GlanceIntentAnswers.swift`: `dueNext`/`dueToday`/the
internal `answer(...)` gained `appLockIsEnabled: Bool = false`. When `true`, the function returns
`.message(.unavailable)` before touching the glance at all — the same "Open Tally to see what's
due." message the widgets already show for `.signedOut`/`.unavailable` (`GlanceText.swift:86`), so
**no new copy is needed**: the SEC-1 report's own optional-fix text names this exact string
(`L10n.Widgets.messageOpenTally`). The function stays pure (no Keychain access), so the gate is
directly unit-testable with a plain `Bool`.

`apps/TallyiOS/Tally/Intents/DueIntents.swift`: a new file-private `appLockIsEnabled()` reads
`KeychainAppLockPreferenceStore().load().effective.isEnabled` (the same store and defaults the
composition root uses) and threads it into both intents' `perform()`. This is a read-only boolean
setting, never the glance or any protected content, so it answers the brief's "a read-only lock
flag the intents can read without unlocking data". `.requiresLocalDeviceAuthentication` (SEC-FIX-1)
is untouched — it still forces this iOS device to unlock before `perform()` runs at all; the new
check is independent and additional, because Tally's own in-app App Lock is a separate promise
from "this device is currently unlocked" (a student can turn App Lock on and the rest of the app
honours it regardless of device-unlock state).

Test: `WidgetIntentsTests.swift` — new `dueAnswersStayNeutralWhenAppLockIsOn`: with items present,
both `dueNext`/`dueToday` under `appLockIsEnabled: true` speak only "Open Tally to see what's due."
(never a title or course), the device-unlock policy assertion is re-checked alongside it, and a
control case confirms the same glance speaks normally with the flag off (default).
