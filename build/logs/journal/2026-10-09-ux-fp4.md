## Design decisions

- **D30 (sheet tint): two explicit `.tint(TallyColor.accent)` calls, not one.** Read
  `HomeShellView.swift` closely: `.tint(TallyColor.accent)` is chained directly onto the `TabView`
  node, while `.sheet(item: presentedSheet)` is a modifier on the outer `VStack` — a sibling
  scope, not a descendant of the tint. Wrapping the sheet's `switch` content in a `Group` with its
  own `.tint(...)` (right where the brief points, `HomeShellView.swift:160-171`) fixes Settings,
  and — since Subscription and Family are *pushed* from Settings' own `NavigationStack`, which
  inherits the Group's tint normally — those too, with no separate edit. `SubscriptionSettingsView`
  presents its *own* fresh `.sheet(item: $paywall)` for the Paywall (a second, independent
  presentation of the same screen HomeShellView also presents): added the identical explicit
  `.tint(TallyColor.accent)` there too, rather than relying on inheritance across a second sheet
  boundary I could not verify without a device.
- **D07: one shared `ViewModifier` plus one shared `LabeledContentStyle`**, not per-call-site
  colour literals, per the brief's "ONE shared modifier" rule.
  - `TallySectionText` (`.tallySectionText()`) — `TallyColor.textSecondary` on any header/footer
    `Text`. Applied directly inside each `header:`/`footer:` closure (never on the `Section`
    itself, which would also recolour the section's *content*, not just its header/footer).
  - `TallyLabeledContentStyle` (`.labeledContentStyle(.tallySecondaryValue)`) — a custom
    `LabeledContentStyle` wraps `configuration.content` in `.foregroundStyle(TallyColor.textSecondary)`
    explicitly, applied *once* per `Form` (Settings, Subscription), rather than converting every
    `LabeledContent(_:value:)` convenience call to its closure form by hand. (A single
    `.foregroundStyle` set ambiently on the Form would recolour via SwiftUI's *hierarchical*
    `.secondary` resolution — a dimmed variant of whatever primary is in scope, not a literal
    `textSecondary` — so a real style override was used instead of a shortcut.)
  - `CourseDetailView.swift`: `Section(section.title)`'s own implicit header (the assignments
    list) also rendered the same under-contrast grey; converted to an explicit `header: { Text(...) }`
    so it could take the same modifier — the only structural change in this defect's fix.
  - `Insights/ScreenCharts.swift`'s `CategoryWeightsChart` is the *one* component behind both
    "Course detail" and "Insights" category-weight charts (confirmed: `grep` shows exactly one
    `struct CategoryWeightsChart`, called from `CourseDetailView.swift:170` and
    `InsightsScreen.swift:37`) — its y-axis `AxisValueLabel` needed one `.chartYAxis { ... }`
    block, fixing both call sites at once.
  - Scope: fixed every header/footer/`LabeledContent` in Course detail, the Grades tab (the
    category table inside Course detail), the What-If *header* inside Course detail (the entry
    point to the sheet), To-Do, Calendar, Settings (+ its embedded Linked-students/Reminders/
    Family-sharing sections), Subscription and Family (including the Family-area sheets:
    AddStudentSheet, InviteSheet, PairingCodeSection — same root cause, same feature area, even
    though the audit's "Where" column names only the top-level screens). Deliberately **left**
    `WhatIfSheet.swift`'s own internal category-group headers (lines ~39-45, 254-256, 429-431)
    untouched — same under-contrast pattern, but not named in D07's "Where" list and not something
    the audit flagged; recorded as an open item instead of fixed, per rule 9 ("fix only your
    package's defects... if you see another, record it, don't fix it").
- **D10: move `.frame(minHeight: 44).contentShape(Rectangle())` inside the label**, before the
  button style, for every control the defect names. `WhatIfSheet.swift`'s existing chips already
  *had* `.frame(minHeight: 44)` — but chained *after* `.buttonStyle(.bordered)`, which is exactly
  the bug D10 describes for "See Plans" before its own FP-2 fix: the modifier grows the view's own
  layout box, not the `.bordered` style's actual hit-region. Converted `Button(title) { action }`
  convenience calls to `Button { action } label: { Text(...).frame(minHeight: 44).contentShape(Rectangle()) }`
  for Paywall Restore/Redeem, the two `PaywallLegalLinks` (`Link`, not `Button` — same fix, `Link`
  takes a label closure too), the What-If chips (moved inside, ahead of `.buttonStyle(.bordered)`),
  and School search's Retry (inside `TallyUnavailableView`'s `actions:` closure). Added
  `testPaywallLinksMeetTheMinimumHitTarget` (`PaywallUITests.swift`) asserting `frame.height >= 44`
  for `paywall.restore`/`.redeem`/`.terms`/`.privacy`, mirroring the existing stepper-button frame
  assertion in `CourseDetailUITests.swift`.
- **D12**: `.frame(width: 28)` on `PaywallFeatures`' icon, matching `WelcomeView.swift`'s
  `BenefitRow` exactly (same fixed width, same position in the modifier chain — before
  `.accessibilityHidden`). No font change: the defect is the ragged left edge, not the icon's size.
- **S3 — What-If chip consistency: no code change (decision only).** `.tallySecondary`'s label
  colour is `accent` via `.tint`, which is exactly what ux-fp6's own D32 measured at 4.02:1 in
  dark on the chip's `bgCard` background — below 4.5:1. The chips' `textPrimary` label (from D32,
  already merged) is the only one of the two that clears ≥ 4.5:1 in both appearances; matching
  "every other bordered button" would regress D32. Decision: keep `textPrimary`; the visual
  difference from `.tallySecondary` CTAs is read as appropriate (compact in-row selectors vs.
  primary/secondary calls to action), not an unresolved inconsistency.
- **S3 — Increase Contrast.** Added a High Contrast appearance to `accent.fill.colorset`: Any
  `#123C80` (reusing `accent`'s *own* High Contrast Any value — both tokens already share the same
  normal-contrast Any, `#1D4E9E`), Dark `#1F4690` (computed, not reused — `accent`'s dark HC moves
  *lighter* since `accent` is foreground text there, but `accent.fill` is always a background
  *fill* behind a white label in both appearances, so its HC needs to go *darker*, same direction
  as light). Computed white-on-fill contrast with the WCAG relative-luminance formula: light
  7.97:1 → 10.59:1, dark 5.99:1 → 8.98:1 — both a meaningful step up, dark (the binding floor)
  gaining the most. **UNVERIFIED on a device**: the audit tour has no Increase Contrast capture to
  measure from; flagged as an open item.
  **Form bar (declined, explicitly).** Evaluated swapping `FormSheetBar`'s fixed hex
  (`#F2F2F7`/`#1C1C1E`) for `Color(uiColor: .systemGroupedBackground)` to pick up Increase Contrast
  automatically. `ScreenChrome.swift`'s own round-3 comment already flags that this UIKit colour
  might resolve at the sheet's *base* level (`#000000` dark) rather than the *elevated* level
  (`#1C1C1E`) it was deliberately set to match — a question that round deliberately left
  unresolved for the same reason I can't resolve it now (no device, no Xcode on this host). Making
  the swap risks silently regressing an already-verified D01 fix to chase a minor HC benefit on a
  background bar; declined. Not implemented.
- **S3 — Welcome AX5 grey haze.** `WelcomeView.swift`'s `ScrollView` has no nav bar
  (`.toolbar(.hidden, for: .navigationBar)`) and never picked up `tallyScreenChrome()`/
  `tallyLargeTitleScreenChrome()` at all (not even the half of it that doesn't need a toolbar) —
  so the tall navy brand panel scrolling under the status bar at AX5 got the system's default
  `.soft` scroll-edge fade instead of D01's `.hard` edge. Added
  `.scrollEdgeEffectStyle(.hard, for: .top)` alone (the `toolbarBackground` half of
  `tallyScreenChrome()` is moot with no bar). Confirmed ours: `WelcomeView.swift` is squarely in
  this package's `TallyFeatures` ownership, the exact same fix pattern already proven across every
  other D01 screen.
