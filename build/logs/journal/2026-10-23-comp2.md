### Trusting the code over the backlog row (rule 8)

- EB-26's row says "Add 'Erase Saved Data' ... to the school-off notice." The brief's own Scope
  section additionally says "Sign Out & Erase and the PAY-10 school-revoked notice stay as they
  are." Read together: the notice's *existing* three buttons and their behaviour are unchanged;
  "Erase Saved Data" is a new, fourth, additive button on the same notice. That is what shipped.
- `AccountSignOut.purge` (the function EB-26's row says to reuse) unconditionally removes the
  account from `accounts.json` and resets the app-lock setting — i.e. it *is* sign-out from the
  account record's perspective, so it cannot be called "without signing out" as written. Added a
  new, narrower primitive instead (`SignOutUseCase.eraseSavedData` / `AccountSignOut.eraseSavedData`)
  that reuses only `SignOutUseCase`'s steps 2–3 (cancel notifications; crypto-shred and delete the
  store files via `AccountPurger.purge`), never step 1 (revoke) or step 4 (delete the credential).
  `accounts.json` and the app-lock setting are never touched by it.
- EB-20's row says notification content should include "plan, amount, period". The brief's own
  Scope bullet says "never a price or grade in the notification beyond what the backlog allows",
  and the codebase's own established rule (`L10n+Subscription.swift`'s header: "Prices are never
  here") plus every existing generic notification's Lock-Screen-safe wording agree with the
  brief, not the backlog's "amount" word. Shipped generic, price-free wording; flagged in the
  report rather than silently picking a side.

## EB-26 (retention after the school turns Tally off)

- `RefreshRecord` (`FreshnessPolicy.swift`) gains `schoolDisabledSince: Date?`: set once, the
  first time `failed(.schoolDisabled, at:)` is recorded, left alone by a repeat of the same
  failure (so a daily background retry never pushes the window out), cleared by `succeeded` or
  any other failure category. A new Optional field decodes safely from an old persisted blob with
  no version bump (`RefreshStateStore.currentVersion` unchanged).
- `SubscriptionConfig.schoolRevokedRetentionDays = 30` (the owner's number, not counsel's).
- New pure type `SchoolRevokedRetention.isExpired(_:now:retentionDays:)` (TallyDomain): the only
  place that reads the field against the config.
- New `SignOutUseCase.eraseSavedData` / `AccountSignOut.eraseSavedData` (see above): the "Erase
  Saved Data" purge path, reused by both the manual button and the automatic expiry.
- `RefreshCoordinator.eraseLocalData()`: the in-memory half (drops `committedSnapshot` and
  resets `record`, like `bumpEpochAndCancel()`, but never `shutdown()`s — a later `run(trigger:)`
  on the same coordinator still fetches, because the account is never signed out of). Needed so
  the Home stops showing the erased in-memory snapshot the instant the student taps the button,
  without giving up the coordinator's ability to resume once the school re-enables Tally.
- `LaunchBootstrapper`: new step `schoolRevokedRetention`, probed unconditionally (every launch
  that has an account), right after the refresh record is read. When `SchoolRevokedRetention
  .isExpired` says so, it calls `AccountSignOut.eraseSavedData` before this resolution hands back
  a glance or a record, so the first paint never shows data that is about to be (or just was)
  erased. **Exact-list rule**: added `schoolRevokedRetention` to `LaunchTests.swift`'s step-list
  array and its three order assertions in this same commit (agent rule 15; PRs #60/#71 the brief
  cites both failed CI on exactly this).
- `AppModel.eraseSavedData()`: the manual button's entry point. Closes the notice, erases the
  coordinator's in-memory state, then off the main actor purges the files and reloads the widgets.
- `SchoolRevokedNoticeView`: added "Erase Saved Data" (destructive role) beside the unchanged
  "Continue with Saved Data", confirmed through the shared, already-AX5-audited
  `tallyDestructiveConfirmation` component (D03 round 2's fix, reused rather than a hand-rolled
  `.alert`), and a footnote stating the automatic-expiry window, composed from
  `L10n.Subscription.days(_:)` (never a raw number, so the plural form stays correct).
- New DEBUG/`TALLY_TEST_HOOKS`-only launch hook `TallyTestHooks.schoolRevoked` (`LaunchTestHooks
  .swift`), mirroring `lastRefreshAttempt`'s own pattern: writes the active account's refresh
  record as already failed with `.schoolDisabled` 60 s ago (so the launch refresh is throttled and
  does not immediately clear it), so a UI test can reach the notice deterministically.

## EB-20 (on-device renewal reminders)

- `SubscriptionFacts.willAutoRenew: Bool` (default `false`), read only from verified renewal info
  (`StoreKitEntitlementSource`, same trust rule as the existing `gracePeriodExpirationDate`) — the
  codebase had never read `Product.SubscriptionInfo.RenewalInfo.willAutoRenew` before this.
- New pure type `RenewalReminderPlan` (TallyDomain): `plan(_:role:products:holding:now:)` returns
  the 40- and 20-day-before reminders due right now (empty whenever auto-renew is off, the
  renewal date has passed, nothing is `.subscribed`, or `holding == .schoolSeat` — the school, not
  the student, manages that purchase, M3-B3's own rule extended here); `diff(desired:pending:role:)`
  is the pure schedule/cancel decision a reconcile pass needs, so the cancellation-on-auto-renew-off
  path is unit-tested without any platform or StoreKit double.
- `NotificationKind.renewalReminder` + `ReminderContent.generic(for:)`'s new case: generic,
  Lock-Screen-safe wording ("Open Tally to manage your subscription."), matching every sibling
  kind's own "Open Tally to ..." convention (`UNNotificationSchedulerTests
  .defaultContentIsGeneric` asserts every kind's body has that prefix — checked against this
  wording specifically before picking it).
- `SubscriptionEngine.apply` now also takes the verification's own `facts` (nil on the `.launch`
  reason's first, Keychain-only pass; the real StoreKit facts on every verified pass) and, once an
  account is attached, reconciles the two reminders directly through `environment.notifications`'
  base `NotificationScheduling` — never through `ReminderPipeline`/`ReminderPlanner`, which plan
  from a Canvas snapshot this has nothing to do with. `SubscriptionStatus`/`SubscriptionModel` gain
  `hasUpcomingRenewalReminder`, mirrored the same way every other field already is.
- `SubscriptionSettingsView`: a new banner, shown only while `hasUpcomingRenewalReminder` is true
  and `RemindersModel.permission` is not `.authorized` — reusing `RemindersViewCopy.turnOn`/
  `.openSettings` verbatim (the same iOS permission already covers both reminder kinds, so nothing
  subscription-specific needs asking for).
- Verified `HookEntitlementSource` (the UI-test StoreKit stand-in every existing UI test uses via
  `TestHooks.entitled`) never sets `willAutoRenew`, so it defaults `false` and every existing UI
  test's `RenewalReminderPlan.plan` call returns empty — this package adds no new behaviour any
  existing test could observe. Confirmed by reading `SubscriptionTestHooks.swift` and
  `SubscriptionEngineTests.swift`/`SubscriptionTestSupport.swift`'s fixtures line by line; no
  dedicated UI-test hook exists yet to put a renewal inside the 40-day window on demand, so the
  banner itself is not exercised by a UI test (open item below) — building one was judged outside
  this package's "M" size and the LEAN CI budget.
