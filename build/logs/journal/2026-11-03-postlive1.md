## Regression found in PR #102's run (41645820079), fixed before the round-2 push

Read back the failed run in full (`gh run view 41645820079 --log-failed`) before changing
anything, per rule 8 ("if a document is wrong about the code, trust the code... continue") and
rule 4 ("a warning for a test in your own files is your bug"). Every test failure across all
4 failing jobs (`iOS ThreadSanitizer`, `iOS build + test` main run, its deployment-floor run, and
`iOS AddressSanitizer`) was the exact same one assertion:
`ReminderPipelineTests.nothingInThePast()` ("a cache more than a day old: the stale-data warning
is not scheduled in the past (planner finding P-1)", `RemindersTests.swift:484`). One separate,
unrelated failure (`TallyCore perf gates (Linux, release, non-blocking)`: `GoalSeek.solve`'s
median over its ceiling) is explicitly non-blocking by its own job name, is not in the required-
jobs list, and touches nothing this work package changed -- left as an open item, not fixed.

- **Root cause (my own bug, introduced by item 3's first fix):** `nothingInThePast()`'s own
  comment says it plainly -- "the flagship is fetched now (`FlagshipAccountGateway`), so its
  warning is due in 24h; the pass runs 3 days later" (`ReminderRig(now: Date()
  .addingTimeInterval(3 * 24 * 3600))`). That test deliberately needs the snapshot's `fetchedAt`
  to be the TRUE, unshifted real clock, while `rig.now` (the pass's clock) is artificially 3 days
  ahead of it -- that gap is the staleness the test exists to prove is handled. Item 3's first
  fix threaded `rig.now` into `FlagshipAccountGateway.flagship(account:now:)` unconditionally
  for every `ReminderRig.coordinator()` caller, which collapsed `fetchedAt` to equal `now` here
  too, eliminating the staleness and breaking the test's whole premise -- confirmed exactly by
  the failure's own printed value, `"Tally hasn't refreshed since yesterday at 9:01 AM"` is for
  a `fetchedAt` that is NOT 3 days old any more, so the sentinel's fire date was no longer in the
  past, so it stayed scheduled, so the `== nil` assertion failed.
- **Fix:** reverted `coordinator()`'s unconditional change; it now takes an optional
  `fetchedAtOverride: Date? = nil` parameter. `nil` (every existing call site, unchanged)
  preserves the ORIGINAL behaviour exactly -- `FlagshipAccountGateway.flagship(account:)` with no
  `now:`, a real, independent `Date()` read, restoring `nothingInThePast()`'s needed gap. Only
  `defaultLocaleMatchesTallyLocaleEffective` (the actual flaky test) now passes an explicit,
  shared `let sharedFetchedAt = Date()` to BOTH its rigs' `coordinator(fetchedAtOverride:)`
  calls, so their two snapshots share one `fetchedAt` by construction -- fixing the original
  flake without touching `fetchedAt` for anyone else.
- Checked every other `ReminderRig(now:)` call site again for the same "needs a real-time gap"
  shape: only `nothingInThePast()` passes a non-default `now:`; every other rig uses the default
  `ReminderTestSupport.anchor`, and none of them read or assert on `fetchedAt`/staleness wording,
  so none of them were ever at risk the same way.
- UNVERIFIED by local build (still no Xcode on this host) -- read back twice by hand, and
  re-traced the exact failure value (`"...since yesterday at 9:01 AM"`, printed by the CI run
  itself) against the new code's logic before trusting the fix. The next PR run is the real
