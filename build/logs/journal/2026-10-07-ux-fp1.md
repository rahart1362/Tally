## D01 (S1) — content under bar titles

Chosen over `.toolbarBackground(...) + .toolbarBackgroundVisibility(.visible, ...)` because it is
the API iOS 26 itself exposes for this exact problem (how much the scroll-edge effect occludes vs.
fades content) without swapping the bar's own Liquid Glass material for a flat fill — the
acceptance criterion says "the bar still reads as native iOS 26." Applied via `tallyScreenChrome()`
to: `DashboardView`, `InsightsScreen` (ScrollView); `CoursesScreen`, `ToDoScreen` (select mode
included — same List), `CalendarScreen`, `CourseDetailView`, `WhatIfSheet` (List); `SettingsView`,
`PerCourseThresholdsView`, `WhatTallyStoresView`, `SubscriptionSettingsView`, `PaywallView`,
`StudentDetailView`, `AddStudentSheet`, `ObserverDetailView`, `HowToRemoveSheet`, `InviteSheet`
(every Settings/Subscription/Family Form and the Paywall sheet, per D01's acceptance list).

Not applied to `SchoolSearchView` (onboarding, not in D01's named screen list) or to Lock.

### D31 (S2) — rows still system grey, round 2

The verdict's own diagnosis: round 1's `.listRowBackground(TallyColor.bgCard)` sat on `TallyListChrome`,
applied to the `List` itself — a list-row trait like this only reaches an actual row producer (a
`Section`, a `ForEach`, or a plain row view), never the `List` as a whole. Removed it from
`TallyListChrome` and added a new `TallyRow`/`tallyRow()` (`ScreenChrome.swift:96-115`), applied
directly to every row/Section instead: `CoursesScreen.swift` (the bare `ForEach`, no `Section`),
`ToDoScreen.swift`, `CalendarScreen.swift` (both its Sections), `CourseDetailView.swift` (11 Sections
— every one except the hero's, which keeps its own `.listRowBackground(Color.clear)`),
`WhatIfSheet.swift` (4 Sections, including the two separate `WhatIfWeightsSection`/
`WhatIfGoalSection` structs' own), `StudentSwitcher.swift`'s `StudentSwitcherSheet` (both Sections).

Applying a row-level trait to a `Section` (rather than to each row inside it one at a time) reaches
every row the Section contains — this is documented, standard `List` styling behaviour, and the
pattern this package's own round-1 code already relied on for the hero's `.listRowBackground
(Color.clear)` override winning over a more general default. Verified by grep that every `Section`
and every bare row-producing `ForEach` in the six touched files now carries `.tallyRow()` (except
the hero, deliberately).

What-If's score field and the category-weight field were still pure black regardless:
`.textFieldStyle(.roundedBorder)` was never actually transparent against a `bgCard` row the way
round 1's own comment assumed — its fill is opaque, and round 1's separator-stroke overlay only
added an outline on top of that still-black fill. Switched both to `.textFieldStyle(.plain)` with an
explicit `TallyColor.bgCanvas` fill (`RoundedRectangle(cornerRadius: TallyRadius.iconTile)`) and the
same separator stroke (`WhatIfSheet.swift:144-160,286-308`). `bgCanvas` is darker than `bgCard` in
dark mode (`#05080F` vs `#111827`, confirmed from `Colors.xcassets` directly) and lighter in light
mode (`#F2F4F8` vs `#FFFFFF`) — either way it reads as a recessed input against the row around it,
which is the acceptance criterion's "at most two dark surface tones" by construction (bgCanvas is
one of the two allowed tones). The score stepper's capsule got a matching separator stroke
(`:359-365`) per the fix list's own text.

### R1 (S2) — School search field clips/no glyph at AX5

`.navigationBarDrawer(displayMode: .always)` is still a real `UISearchBar` under the hood, and a
`UISearchBar` has no supported way to wrap its text, force a glyph to render, or scale its
placeholder independently of the system's own sizing — exactly the three things the verdict found
broken. The fix list's own call: replace it at accessibility sizes with a plain SwiftUI field.
`SchoolSearchView.swift:46-70` now branches on `typeSize.isAccessibilitySize`: below it,
`.searchable` is untouched; at and above it, a `TextField(..., axis: .vertical)` in its own
`.safeAreaInset(edge: .top)` (`accessibleSearchField`, `:90-111`) — `TallyTypography.body` (scales
with Dynamic Type, unlike the old placeholder), an explicit `magnifyingglass` `Image`,
`TallySpacing.screenMargin` padding. `axis: .vertical` is what actually fixes the clipping: the
field grows a second line instead of clipping the leading edge of a long query.

Gave it `.accessibilityIdentifier("schoolSearch.field")` per the fix list's "keep the search
field's accessibility identifier." Traced what currently finds this field, though: every test that
touches it (`SchoolSearchUITests`, `SampleDataUITests`, `PaywallUITests`, `SignInSignOutUITests`,
and — the one that matters here — `AuditTourUITests.swift`'s `testH_welcomeAndSchoolSearch` and
`signInToDemoSchool`) queries `app.searchFields.firstMatch`, a TYPE query (`XCUIElementTypeSearchField`),
not an identifier one; there was no existing identifier to "keep." A plain `TextField` reports as
`XCUIElementTypeTextField`, which `app.searchFields` will never match, at AX5 specifically. Not
mine to fix (`AuditTourUITests.swift` is PR #41's file, outside this package per rule 9) — recorded
as an open item below rather than guessed around with a parallel, duplicate search affordance just
to keep an old query working. The DEBUG launch-probe overlay (`LaunchTestHookViews.swift`) was NOT
touched: round 1's coverage bug traced to `.navigationBarDrawer` being UIKit nav-bar chrome, which
does not reliably participate in an ancestor SwiftUI `safeAreaInset` reservation the way a plain
SwiftUI view (what the field is now) does — nested `safeAreaInset(edge: .top)` calls are
well-defined, already-proven-in-this-codebase behaviour (`CalendarScreen.swift`'s own breadcrumb +
week-strip stacking), so replacing the UIKit control should resolve the coverage as a side effect.
UNVERIFIED by a real capture (see "Blocked" in the report) — this reasoning, not a screenshot, is
the current evidence.

### A real bug found on the first push (not assumed fixed)

`.tallyRow()` after. Grepped the whole package for `.onMove`/`.onDelete`/`.onInsert` afterward —
this was the only site using any of the three, so it's the only place this exact mistake could
have happened.
