## Design decisions

- **`accent.fill` (new token), not a label-colour fix alone.** `accent` must keep its own Dark
  appearance (#8DB4FF) — it is the tint for the TabView, icons, links and the What-If slider, all
  already legible on `bg.canvas`/`bg.card`. A *second*, always-dark fill token
  (`accent.fill`: Any #1D4E9E, Dark #2E5FBF) is the one the audit's own fix list asks for, and it
  is the only approach that also fixes the swipe actions (`.swipeActions` buttons always draw a
  white label, which a label-colour change can't reach).
- **`accent.onFill` is retargeted, not duplicated.** Its only two call sites
  (`SignInHandoffView`'s `ProgressView` tint, `SampleDataBanner`'s `foregroundStyle`) both sit on a
  background that is moving to `accentFill` in this same work package, so its old Dark override
  (#06142B, correct only for labelling the *lighter* `accent` in dark) is replaced with the same
  white as Any — matching what `accentFill` needs in both appearances. No third token.
- **One central fix for D28's "by code" list.** `TallyPrimaryButtonStyle` (`ButtonStyles.swift`) is
  the single style behind `.tallyPrimary`, used by Welcome's "Find My School", Paywall's "Start
  Free Trial"/"Subscribe", App Lock's "Unlock with Face ID", first-sync "Retry", the sign-in
  hand-off's "Continue to …", SchoolNotEnabled's "Ask My School", SchoolRevoked's "Manage",
  SubscriptionLockViews' "See Plans", and GradeNotInCanvasInfo's "Tell My School" — tinting it with
  `accentFill` fixes every one in a single edit, per the "systemic fixes go into ONE shared
  modifier" rule.
- **Two more explicit call sites D28 needs.** `RemindersTipCard`'s "Turn On Reminders"
  (`.borderedProminent` + `.tint(accent)` directly, not `.tallyPrimary`) and both To-Do swipe
  buttons (`ToDoScreen.swift`): the "Done"/"Not done" button already had an explicit
  `.tint(accent)` to retarget; "Open in Canvas" had **no** explicit tint at all and was inheriting
  `accent` from `HomeShellView`'s TabView-level `.tint(TallyColor.accent)` — found only by reading
  the call site, not from the defect's own file hints.
- **D29: colour only.** UX-FP1 already fixed the safe-area part (`ignoresSafeAreaEdges: []`, so
  the status bar sits on `bg.canvas`, not the band). D29's remaining ask is `SampleDataBanner`'s
  own `.background(accent, …)` → `accentFill`; its text already uses `accentOnFill`, now white in
  both appearances from the D28 token change.
- **D32: `textPrimary`, not a new high-contrast accent.** The audit's fix list offers either; the
  existing `textPrimary` token is already >= 4.5:1 on `bgCard` in both appearances (it is near-black
  Any, near-white Dark), so no new token was needed for the What-If quick-fill chips.
- **D33: lighten `bg.brand`'s Dark appearance AND keep the hairline.** The brief says "and/or"; I
  did both; the audit's own computed numbers for the lighter navy (#0D2A55) still land the hero
  only ≈1.25:1 off `bg.card`, which reads as a close call for "the hero stops being the strongest
  block" — the 1 pt `separator` hairline (dark only; light needs none) is cheap insurance for the
  same defect, not a second, redundant fix. One shared modifier, `tallyHeroBackground()`
  (`ScreenChrome.swift`), replaces the `background(bgBrand, in: RoundedRectangle(...))` call at all
  three sites (Dashboard's loading skeleton, Dashboard's loaded hero, Course Detail's hero).
  `bg.brand`'s other call sites (Welcome's brand panel, Paywall's T-mark tile) pick up the same
  lighter Dark value automatically from the asset catalog, with no code change and no stroke (not
  "hero shapes," not named in D33, and they sit against `bg.canvas`, not `bg.card`).
- **No regression test added.** Rule: "add a regression check for each S1 you fix where it's
  cheap." D28/D29/D32 are S2, D33 is S3 — none are S1, so none is required. All four are colour-
  token/tint changes with no layout or identifier change, so the existing UI tests (identifier- and
  layout-based) are expected to stay green untouched.
- **No string changes.** Every fix here is a colour/tint/background change; no copy, no new
  `L10n` key. Strings pending owner approval: **none**.

### Small item 3 — root-cause note

`testB_coursesAndFirstCourseDetail`'s "Failed to determine hittability of \"Courses\" Button:
Activation point invalid" (run 37880767365, Pro Max light AX5) and `testE_toDo`'s missing swipe +
missing select-mode captures read, on inspection, as **one shared cause at that leg**: a gesture
landing on the floating tab bar instead of its intended target (a tab-bar button hit mid-
transition in B; a swipe on a row whose centre sat under the tab bar in E) can silently misfire or
knock the tour onto a different tab, after which the next expected element never appears and
`go`'s tolerant "missing-<state>" path records it. Both fixes avoid touching the tab bar's hit
region in the first place (settle-before-tap; pick a row that clears it) rather than recovering
after the fact.
