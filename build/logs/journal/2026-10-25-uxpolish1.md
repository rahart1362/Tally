## Round 2: UX2-10's Course Options fix didn't fire (found via the Audit tour, before the PR)

Per rule 14 ("Check every changed screen... before the PR"), reviewed every leg of the Audit tour
(run 40188312337, 12 legs, all green) at 200% before opening the PR, rather than trusting the green
run as evidence. Calendar's AX1+ sheet (`48-calendar-optionsMenu.png`, std/ax5/xxxLarge, both
phones, light/dark) and the Dashboard/widget changes (UX2-14, UX2-18) all render exactly as
intended -- see the per-item summary below. Course Options did not:
`audit-en-smallest-light-ax5/302-course1-gradesOutsideCanvas.png` and
`audit-en-smallest-light-ax5/301-course1-menu.png` (the screen right after the FIRST tap on
`courseDetail.menu`) are pixel-identical, and both are pixel-identical to the ORIGINAL (pre-PR)
`pmo-audit/.build-audit/final-tour/run40042251418/audit-en-smallest-light-ax5/
302-course1-gradesOutsideCanvas.png` -- the exact cut-off popover UX2-10 reported, unchanged by my
first patch.

Diagnosis: `GradeOverrideMenu`'s `if typeSize.isAccessibilitySize { ... } else { ... }` branch is
INSIDE the `Menu`'s own content closure (`Menu { if ... } label: { ... }`), unlike
`CalendarScreen.swift`'s options button, where the identical check wraps the WHOLE toolbar item,
picking between a `Button` and a `Menu` before either is built. Calendar's sheet rendered
correctly on the same AX5 leg (confirmed: `48-calendar-optionsMenu.png` shows the full-screen
`TallyOptionsSheet`, title, tinted Subscribe button, Cancel). Course Options' own nested check
never saw `typeSize.isAccessibilitySize == true`, so it kept taking the flattened-`Section` branch
(Menu's own anchored-popover rendering, UX1-19's original defect) at EVERY tap, both before tapping
("301-course1-menu") and after ("302-...-gradesOutsideCanvas", the same screen, because nothing
had actually changed). This reads as a `Menu` content closure not tracking a live `@Environment`
read the way the rest of the view tree does on this iOS version -- plausible given `Menu`'s content
is bridged into a system `UIMenu`, but not independently confirmed beyond this evidence (no Xcode
on this host to step through SwiftUI internals).

Fix (same commit as this entry, `CourseDetailView.swift`): restructured `GradeOverrideMenu.body` to
match Calendar's proven shape exactly -- the `typeSize.isAccessibilitySize` check now wraps the
WHOLE control (`if ... { Button -> .sheet(TallyOptionsSheet) } else { Menu { flattened Section } }`),
never nesting a size check inside a `Menu`'s own content. This also removes the now-unreachable
`confirmationDialog` and the two-step flow (toolbar tap -> single menu row -> dialog/sheet)
entirely; AX1+ now opens the sheet in one tap, which needed no test changes --
`AuditTourUITests.testB2`'s own `else-if` already falls through gracefully to the "flattened"
(now: direct-sheet) branch when `courseDetail.gradesOutsideCanvas.automatic` exists immediately
after the first tap, and `AccessibilityAuditUITests.a11yReachCourseOptions` checks either identifier
already. Renamed `isChoiceDialogPresented` -> `isChoiceSheetPresented` (grepped the repo: no other
reference). Local checks re-run clean (lint 0/320, view-bodies/l10n/catalog/debug-symbol scripts all
PASS). This needed a second CI/Audit-tour pass beyond the brief's literal "ONE" budget -- recorded
here and in the hand-off reply, since shipping the round-1 patch unverified would have left UX2-10
not actually fixed despite a green run.
