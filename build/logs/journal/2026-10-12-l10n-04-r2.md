## Iteration 2 — CI: four real bugs found and fixed, one per push (commits `8ce19bc`, `b22cee3`, `7658e85`, `d677b86`)

PR run 38188594780 (round 1's) was confirmed green before pushing. Each push below re-ran the PR's
own CI (this round's "iteration runs" *are* those PR re-runs — the brief's quick-dispatch budget
was not separately spent, since every push already re-runs the full required-job suite).

1. Push `d533a19` → run 38195787377: failed. `GlanceLocaleOverride.swift:38: cannot find
   'TallyLocale' in scope` — the new file imported `SwiftUI` but not `TallyStrings` (where
   `TallyLocale` lives), unlike every sibling file in the package. Fixed, commit `8ce19bc`.
2. Push `8ce19bc` → run 38196505757: failed differently.
   `SettingsView.swift:321: error: argument passed to call that takes no arguments` —
   `Character.uppercased()` takes no locale argument (only `String.uppercased(with:)` does);
   `name.first` is a `Character`. Fixed by wrapping in `String(...)` first, commit `7658e85`.
   **Also found by inspection before this run's result came back** (not by CI): round 2's catalog
   edits changed ~20 Spanish values that `L10N04SpanishFixture.swift` (a generated fixture,
   "do not hand-edit" per its own header) still carried the old text for —
   `L10N04SpanishResolutionTests.everyPlaceholderFreeKeyResolvesInSpanish` would have failed on all
   of them, and `postFreezeKeysResolveInSpanish` hardcoded the pre-L2-fix
   `courseDetail.override.menuRowTitle` value. Regenerated the fixture
   (`.build-l10n-04-r2/regen_spanish_fixture.py`, 531 rows now — +4 net, mostly one placeholder-free
   key the round-1 generator had missed) and fixed the one hardcoded test expectation. Swept
   `RendererGoldenTests`/`ScreenFormatterLocaleTests`/`L10nLookupTests` for the same risk: none
   affected (en-only, or value-agnostic). Bundled into commit `b22cee3`, pushed alongside the
   `uppercased(with:)` fix's own commit in the same cycle.
3. Push `b22cee3`/`7658e85` → run 38196873833/38197001967 (the queue coalesced to the latter):
   **compiled and ran this time** — but `FamilyUITests.testRemovingEveryStudentShowsTheParentEmpty
   State` and `testUnlinkAsksWithTheSpecCopy` (a different, pre-existing test file, not touched
   this round) failed: "Button (First Match) never appeared". Root cause: that file's own
   `tapConfirmation()` helper and its Cancel lookup find the confirmation dialog's button (as
   opposed to the page's own same-labeled row button, e.g. `family.unlink`) by excluding
   `identifier BEGINSWITH 'family.'`. This round's new identifiers on the *confirmation's own*
   buttons (`family.removeConfirm.destructive`, `family.unlinkConfirm.cancel`, etc.) also started
   with `"family."`, so the same filter now excluded them too — zero matches. Fixed by renaming to
   `familyConfirm.remove.*`/`familyConfirm.unlink.*` (same ids, different prefix): zero changes
   needed in `FamilyUITests.swift` itself. Swept every other `BEGINSWITH`-on-`identifier` predicate
   in the UI test suite for the same collision class (`settings.`/`todo.`/`freshness.` prefixes):
   none found — `SettingsUITests`' own exclusion is an exact `!=` match (confirmed safe by its tests
   passing in run 38197001967 itself), and `ToDoUITests` was already on the prefix-aware
   `elementsWithPrefix` helper from iteration 1. Commit `d677b86`.
4. Push `d677b86` → run 38201921389: **green**, every required job, including the full
   `iOS build + test` suite (FamilyUITests, ToDoUITests, WidgetFamilyRenderTests,
   L10N04SpanishResolutionTests all passing).
