## Design decisions

- **G2 first** (the brief's own order: "G2 — renders you can trust — then D06"). Read
  `WidgetFamilyRenderTests.swift`'s `renderer()`/`png()`/`alpha()` helpers closely: every widget
  view already calls `.containerBackground(...)` in production
  (`GlanceWidgetViews.swift:179`, `GlanceAccessoryViews.swift:34,107,124`), so the gap isn't a
  missing call — it's that `ImageRenderer`, used standalone outside WidgetKit's own host, never
  paints a `containerBackground`'s content at all (confirmed empirically: the pre-fix `m3d-*.png`
  attachments in `audit-proMax-light-std/named/` are plain transparent canvases, flattening to
  black/white depending on viewer — "reviewers had to composite colours by hand" is literally true).
  Added `hostedPNG()`, used **only** by the `snapshot` test: composites, behind the real production
  view, exactly what its own `containerBackground` call already asks for — `TallyColor.bgBrand` for
  the five Home families (`GlanceHomeLayout`), the system's own `AccessoryWidgetBackground()` for
  the two Lock Screen accessories that use it, nothing for the inline accessory (`Color.clear`) —
  plus `TallySpacing.lg` padding for the Home families (the HIG's 16 pt default content margin,
  which a real host applies automatically and a bare `ImageRenderer` does not). Deliberately did
  **not** touch `renderer()`/`alpha()`/`png()` themselves: `accentedKeepsMeaning` depends on the
  *un-backed* alpha channel (an opaque test backdrop would make every pixel opaque regardless of
  data, destroying that test's whole signal), so the functional tests keep the plain renderer and
  only the new `hostedPNG()` is used for the attached-for-review snapshots.
  - First attempt also set `.environment(\.widgetFamily, surface.family)`, which doesn't compile —
    `\.widgetFamily` has no writable key path (confirmed by the compiler, and by precedent:
    `StandingWidgetView` already takes `family` as an explicit init argument for exactly this
    reason). Removed; `Surface.family` is still useful to drive `hostedPNG`'s own background choice.
  - Light **and** dark: looped `ColorScheme` inside the existing `snapshot(surface:mode:)` test
    body (not a third `arguments:` collection — lower risk, and Swift Testing's parameterization
    macro is not something I could verify compiles against a third collection without a device).
    Attachments named `widget-<family>-<mode>-<light|dark>.png` exactly as asked.
- **D06**: `.foregroundStyle(TallyColor.brandCream)` + `.widgetAccentable()` on the checkmark
  (`MarkDoneButton.swift`), per the defect's own suggested fix. `brandCream` is a universal
  (single, non-adaptive) asset colour — confirmed from `brand.cream.colorset/Contents.json` — so
  the fix behaves identically regardless of the system's light/dark setting, matching every other
  brand-surface token (`textOnHero`, `textOnHero2`, `brandGold`) already used alongside it.
  Computed contrast against `bg.brand`'s own Any/Dark hex (`#071A36`/`#0D2A55`, both read from the
  asset, same WCAG relative-luminance method `defects.md` itself uses): **15.56:1 light, 12.73:1
  dark** — both far past the 3:1 floor for a control. Added a CI regression
  (`markDoneButtonGlyphContrast`, S1 per rule): renders `MarkDoneButton` alone on `bg.brand`,
  samples the actual rendered pixels (not a claimed value), finds the pixel that differs most from
  the background corner (the glyph's own fill, whatever colour it is), and asserts ≥ 3:1 — this
  would have failed on the old black glyph (1.21:1) and passes on the fix, in both appearances.
  - Swept every other widget family's glyphs/text for the same "dark glyph on navy" class: every
    other label in `GlanceWidgetViews.swift`/`GlanceListWidgetViews.swift` already routes through
    `GlanceStyle.primary/secondary/accent`, which resolve to `textOnHero`/`textOnHero2`/`brandGold`
    in full colour — computed each against both `bg.brand` appearances (8.33:1 to 17.35:1 range).
    `MarkDoneButton` was the one glyph that bypassed `GlanceStyle` entirely (it lives in the
    `TallyWidgets` extension target, not `TallyGlance`, and never imported it) — the only offender,
    confirmed by code reading, not just by the audit's single D06 row.
- **D23**: compared my first fix's "after" render against the audit's own **composited** "before"
  evidence (`D23.jpg`) and found them visually identical — `GlanceItemList`'s trailing `Spacer`
  already reached the real bottom edge *before* any change of mine (my `.frame(maxHeight: .infinity,
  alignment: .top)` addition was inert), so "1 overdue" was never actually adrift; the whole
  ~100 pt+ of slack landed in one block between the last row and the footer, on a glance that
  simply doesn't have enough upcoming items to fill a 382 pt widget (the other suggested fix, "show
  more rows", would not move the needle here — `weekAheadRows` is already above this fixture's
  4-item count). Added a second `Spacer(minLength: TallySpacing.lg)` between the week strip and the
  item list, splitting the one dead block into two smaller, more deliberate-looking gaps — genuinely
  visible in the "after" capture (confirmed below), and independent of how many items a given
  glance has.
- **D24**: replaced `HeroSilhouette` (a 160 pt navy rounded rect with a leading-aligned 48 pt
  T-mark on an otherwise blank `bg.canvas` page) with a full `bg.brand` background and a centred
  96 pt `TMark` — the exact brand-panel treatment `WelcomeView.brandPanel` already uses (same
  background token, same mark). The owner's emblem itself (`TMark.swift`) was not touched, only
  called with a size parameter its own public API already supports.
- **Onboarding tint**: first attempt mirrored FP-4's own precedent exactly
  (`.tint(TallyColor.accent)` on `WelcomeFlowView`'s `NavigationStack`) — **did not work**: the
  Audit tour's own capture (`113-schoolSearch-failure.png`) still showed "Retry" in system blue.
  Second attempt moved the `.tint()` to sit directly on the `ContentUnavailableView` inside
  `TallyUnavailableView` (the shared component School search's failure state renders through) —
  **also did not work**, confirmed by a second Audit tour capture. Concluded `ContentUnavailableView`
  genuinely does not honour an ancestor `.tint()` for its action buttons in this SDK (regardless of
  distance). Reverted the inert `.tint()` (dead code, and its doc comment's claim was now false) and
  applied `.foregroundStyle(TallyColor.accent)` directly to "Retry"'s `Text` instead — the same
  mechanism `WelcomeView.BenefitRow`'s icon already uses successfully (confirmed correct colour in
  the verified `111-welcome-default.png` capture). Checked every other `TallyUnavailableView` call
  site in the onboarding stack (`SchoolNotEnabledView`, `FirstSyncSkeletonView`): both already use
  `.buttonStyle(.tallyPrimary/.tallySecondary)`, which paints its own colour directly and was never
  affected by this gap — "Retry" was the one unstyled action. Five more call sites exist outside
  onboarding (Dashboard, Insights, ToDo, CourseDetail, Courses); out of this package's scope, not
  touched, recorded as an open item.
  - This fix has **no device-captured "after"**: both Audit tour dispatches and all 3 CI iteration
    runs were already spent confirming G2/D06/D23/D24 by the time this third attempt landed.
    Labelled UNVERIFIED in the report and owner sheet; will be confirmed or caught by the PR's own
    required run.
