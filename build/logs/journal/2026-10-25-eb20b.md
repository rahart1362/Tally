## Implementation

- **Item 1 (richer content).** `RenewalReminderPlan.Reminder` gained a `renewalDate: Date` field
  (verified, computed once in `plan`). `SubscriptionEngine.reconcileRenewalReminders` encodes it as
  a Unix-timestamp string in `PendingReminder.subjectID` — repurposing that field's existing
  "opaque ID the app layer resolves content from" contract, since there is no Canvas snapshot to
  resolve from here. `UNNotificationScheduler.defaultContent(_:)` decodes it for `.renewalReminder`
  alone and builds `ReminderContent.renewalReminder(planName:renewalDate:displayPrice:)`; any other
  kind, or an undecodable `subjectID`, falls back to the existing generic key. `displayPrice`
  is the named, unused, always-`nil` parameter for the amount (Q37 open). This is the one file
  outside the brief's own reading list I had to touch (`TallyPlatform/UNNotificationScheduler.swift`,
  shared infrastructure) — kept the edit additive (one new static func, one new case in the
  existing `init`'s default parameter) and updated the one test (`defaultContentIsGeneric`) whose
  loop-over-every-`NotificationKind` assumption this directly supersedes.
- **Item 4's engine change came first**, since item 1's content needs scheduling to happen
  regardless of account attachment. Added `notifications: any NotificationScheduling` to
  `SubscriptionEngine`'s init (default `NoOpNotificationScheduling()`, new in
  `SubscriptionPorts.swift`), removed the `environment`-gated condition in `apply()`, and deleted
  the now-dead `lastVerified` catch-up in `accountAttached` (its only reason to exist was that
  `environment` used to be the sole path to a notifications handle; `notifications` is now
  init-injected and account-independent, so the launch's own verified pass already schedules/
  cancels before any account exists). `AppEnvironment.live()` builds one shared
  `UNNotificationScheduler()` and passes it to both the engine and `AccountEnvironment`, matching
  what was already implicit for the general reminders pipeline.
- **`SignOutUseCase`**: both `signOut`'s step 2 and `eraseSavedData` now exclude
  `RenewalReminderPlan.owns` identifiers from the union before cancelling.
- **Item 2 (Home banner)**: factored the Settings banner's condition out into
  `RenewalReminderBannerPolicy.permission(hasUpcomingRenewalReminder:permission:)`
  (`RemindersModel.swift`, beside `ReminderTipPolicy`) and had `SubscriptionSettingsView` delegate
  to it, then added `RenewalReminderHomeBanner`/`RenewalReminderHomeBannerCard`
  (`SubscriptionSettingsView.swift`, reusing the Settings banner's exact strings) and placed it in
  `DashboardView.swift` right after `RemindersTip`. Dismissal is a plain `@State` (session only, no
  store) — no new strings.
- **Item 3 (purchase-time offer)**: `PurchaseConfirmationView` takes an optional `reminders:
  RemindersModel?` now (both call sites — `SubscriptionSettingsView`, `HomeShellView` — pass
  `appModel.reminders`), refreshes permission in its own `.task`, and shows one new row
  (`subscription.confirmation.reminderOffer`, the only brand-new string this package adds) with the
  existing "Turn On Reminders" button when `PurchaseConfirmationModel.showsReminderOffer(permission:)`
  is true.
- **Privacy page**: `site/privacy/index.html`'s "Sign Out & Erase ... deletes all Tally data, keys
  and scheduled reminders" is now inaccurate (the two renewal reminders survive). Proposed wording
  in the hand-off reply; did not touch `site/` per the brief.
