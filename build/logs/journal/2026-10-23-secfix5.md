## Item 1 — SEC2-01 (top priority): the significant-change version is acknowledged too early

`AgeAssuranceModel.swift`: moved `lastAcknowledgedSignificantChangeVersion`'s write from
immediately after `requestAgeAssurance()` returns, to only after `consentOutcome` resolves to
`.granted` or `.notRequired`. Added `unacknowledgedSignificantChangeVersion`, set when the
outcome is `.pending`/`.denied`/`.unavailable`; `listenForAnswers()` now finishes the
acknowledgement if a later `.granted` arrives for that same version. No age value touched either
way — only the version string and the rating-observation baseline, both already-existing fields.

Test: new `AgeAssuranceModelTests.swift` (hosted, `#if DEBUG`) — runs two model instances over the
same fake `InMemoryAgeRequestRecordStore`/`InMemorySignificantChangeVersionStore` pair to simulate
a relaunch, covering `.pending`/`.denied`/`.unavailable` (never acknowledged; the relaunch asks
again) and `.granted` (acknowledged at once; the relaunch does not ask again), plus a
`listenForAnswers` late-`.granted` case. The significant-change trigger is driven through the
`AppStoreAgeRatingReading` seam (a controlled "rating changed" signal) rather than
`TallyConfig.currentReleaseIsSignificantChange`, which is a compile-time `false` constant a test
cannot flip — both feed the identical `evaluate()` path. UNVERIFIED locally (TallyAppleKit is
Apple-only; no Xcode on this host) — CI's `ios-build`/`ios-asan` lanes are the verification.
