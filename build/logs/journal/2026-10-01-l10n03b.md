## Critical fix found while writing locale-matrix tests: catalog placeholders were literal "…"

While writing `ScreenFormatterLocaleTests.swift` (below) and cross-referencing `LocalizationTests.swift`'s
already-proven real-catalog values, I compared my own additions against `git show
c54745d:...Localizable.xcstrings` for a key with a genuine argument (`onboarding.firstSync.connectingTo`
-> `"Connecting to %@…"`) and found every catalog entry I had written used a **literal "…" (U+2026)
character** as my own drafting stand-in for "the argument goes here" — and never replaced it with the
real `%@`/`%lld` (or positional `%1$@`/`%2$lld` for 2+ arguments) format specifier Xcode's String
Catalogs actually require. `check_string_catalogs.py` could not catch this: its `signature()` only
recognizes `%`-prefixed tokens, so a value with no `%` at all has an empty signature, which trivially
"matches" anything, and the Swift `defaultValue` (which does interpolate correctly) is never compared
against the catalog text once it contains `\(...)`, by the checker's own documented design (a fallback
value is never validated). Had this shipped, every one of my new sentence/accessibility keys with an
argument would have rendered the literal characters "…" instead of the real content — e.g. "Due … at
…" instead of "Due today at 2:13 PM" — compiling fine, passing every automated gate, and visible only
on an actual device or in a screenshot.

**Scope and fix**, `.build-l10n03b/fix_placeholders.py` (scratch, git-ignored): parsed
`L10n+GradeScreensSweep.swift` (every function's parameter list and types are mine, known precisely)
to compute the correct specifier for each interpolation, in textual order (position, not deduplicated
by Swift variable identity — confirmed against the pre-existing catalog's own convention: a single
occurrence is plain `%@`/`%lld`; two or more, even repeats of the same argument, are positional
`%1$@`/`%2$@`...). Found and fixed:
- **43 keys** via the script, **1 more by hand** (`courseDetail.gradeDistribution.sentence`: its
  4-argument function signature wraps to a second line, which the script's regex did not match —
  caught by re-auditing the script's own coverage count against a plain `grep -c` of the source file,
  161 zero-arg + 43 fixed + 2 plural ≠ 207 total functions, the discrepancy pointed straight at it).
- **3 plural keys** fixed by hand (`dashboard.changes.count`, `courses.health.missingItemsStillAccepted`,
  `insights.streak.days`): each category is its own independent value string, not derived from one
  `defaultValue`, so the script intentionally skipped these.
- **A second, more serious bug** found during the same re-audit, not a placeholder issue: `whatIfGroupHeader`
  had been designed to take only the weight text, silently **dropping `group.name` from the screen**
  (the original showed "Homework · 30% of grade"; mine would have shown only "30% of grade"). Fixed the
  wrapper's signature (now 2 parameters) and the `WhatIfSheet.swift` call site together.

**Verification, not just re-running the same checker that already missed it once:** wrote a small
renderer (`%1$@`/`%2$lld`/etc. → `[ARG1]`/`[ARG2]`) and ran it over **every** catalog value containing
a `%` — mine and every pre-existing one — to eyeball the substituted result reads sensibly, with no
stray "…", no out-of-range argument index, no dropped word. `check_string_catalogs.py`: still PASS,
495 keys, 0 problems (expected — confirms the checker's blind spot here is real, not a tool I can lean
on for this specific class of bug). `check_localizable_literals.py`: unchanged, PASS. `make lint`: 0
violations, 223 files (expected: only catalog JSON and two lines of Swift changed).

Caught before any CI run was spent on it, let alone before the PR. Recorded here in full because it is
exactly the kind of mistake "exit code 0 is never evidence" exists to guard against, and because the
mechanism (a from-scratch rendering check, not just re-trusting the existing automated gate) is the
reusable lesson, not just the fix.
