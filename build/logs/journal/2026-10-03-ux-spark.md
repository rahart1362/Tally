## Design

- Read `Tally_Antigravity_Build_Kit_Scaffold/01_Product_Requirements.md` §2.B and the owning files:
  `TallyFeatures/Insights/GradeTrend.swift`, `InsightsProjection.swift`, `Courses/CourseCard.swift`,
  `Courses/CoursesScreen.swift`, `CourseDetail/CourseDetailView.swift`,
  `CourseDetail/CourseDetailProjection.swift`, `Courses/ScreenFormatter.swift`,
  `Home/HomeModel.swift`, `Home/HomeProjector.swift`, `Settings/AccountProjection.swift`
  (`ScreenProjections.build`), `Grades/GradeWork.swift`.
- Key finding: `CourseCardBuilder.cards`/`CourseDetailBuilder.details` (and `ScreenProjections.build`,
  called synchronously inside the `HomeProjector` actor) are pure, synchronous functions — they
  cannot call `GradeWork` (every engine call is `async throws`, off the main actor on its own
  dispatch queue). The Insights trend handles this by computing asynchronously in `InsightsModel`,
  owned by `InsightsScreen` via `.task(id: projection.trendInput)`. The sparkline needs the same
  shape, shared by two screens (Courses cards, Course Detail) instead of one.
- Decided **not** to touch `HomeModel.swift`/`AppModel.swift`/`ScreenFormatter.swift` (not in my
  ownership list, not named as shared-additive): `CoursesScreen` already has everything it needs
  (`@Environment(HomeModel.self) private var model`, and `model.insightsScreen.trendInput`, already
  public, already built). A new `@State private var sparklines = CourseSparklineModel()` in
  `CoursesScreen` is computed once via `.task(id: model.insightsScreen.trendInput)` (mirrors
  `InsightsModel.load`'s cache-by-input-equality guard) and passed explicitly — not via SwiftUI
  environment — to both `CourseCardView` (per card) and `CourseDetailView` (the whole model, since
  `CourseDetailView` is only ever reached from `CoursesScreen`'s own `navigationDestination`,
  confirmed by grep: no other call site in `TallyFeatures`). This satisfies "compute once per
  snapshot, off the main actor, reused by both screens, cache keyed by the snapshot" without a new
  shared model object or any change to the Home shell.
- `GradeTrend.compute` already builds `courseSeries` (per course, per graded day) before averaging
  it into the overall trend; added `GradeTrendResult.perCourse: [CanvasID<Course>: [TrendPoint]]`
  from that same array (`zip(input.courses, courseSeries) where series.count >= minimumPoints`) —
  no second `GradeWork` pass. `TrendInput` already excludes courses whose grade isn't `.available`
  (kept outside Canvas, not graded, letters-only, hidden, not yet posted), so the sparkline inherits
  that exclusion for free (PRD's list of "no sparkline" cases), per the brief's "reuse, don't
  reinvent."
- New file `Courses/CourseSparkline.swift`: `CourseSparklineModel` (the MainActor cache/loader,
  mirrors `InsightsModel`), `CourseSparklinePoints`/`CourseSparklineBuilder` (pure: the
  VoiceOver sentence, the <2-points guard restated defensively), `CourseSparklineView` (Swift
  Charts `LineMark` + an end-point-only `PointMark`, hidden axes/legend, `TallyColor.accent`).
- Copy: 3 new catalog keys under `L10n.Courses` (`sparklineTrendUp/Down/Steady`), added to
  `L10n+GradeScreensSweep.swift` and `Resources/Localizable.xcstrings` (English only — the catalog
  ships only `en` today; `check_string_catalogs.py` confirms 0 problems). Draft wording, since the
  freeze: "Trend: up from 82.0 to 87.2 percent" / "…down from…" / "Trend: steady at 87.2 percent".
  **Translator note: added after the M3 string freeze — owner approval needed.**
- Layout: the sparkline is only wrapped in the AX-size-aware `AnyLayout` (HStack normally, VStack at
  AX sizes) in the branch that actually has one, so a course with no sparkline keeps its original
  row with no stray spacing for an empty slot (caught this in review before any CI run, fixed by
  duplicating the plain-row branch rather than feeding an `EmptyView` into the custom layout).
- Open question I could not resolve by reading alone (no Xcode/simulator on this host): whether
  `.accessibilityIdentifier("course.sparkline")`, nested inside `NavigationLink`'s label (the whole
  card), survives as an independently queryable XCUITest element, or is swallowed by the
  NavigationLink's own `.accessibilityLabel`/implicit single-element behavior. Same question for
  `courseDetail.sparkline` nested inside the hero's `.accessibilityElement(children: .combine)`.
  Reasoned from SwiftUI's documented accessibility model (an explicit nested
  `.accessibilityElement(children: .ignore)` + its own identifier is the standard way to expose one
  distinct sub-element inside a larger control/combined region) and proceeded; the first CI
  `scope=quick` run (its UI-test job) is the actual verification, per the brief's own call-out
  ("since a UI test matters").
