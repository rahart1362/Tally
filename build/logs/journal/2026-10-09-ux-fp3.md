## Design decisions

- **UX-SPARK-2's style, drawn with Swift Charts marks, not a hand-rolled Canvas.** `LineMark`,
  `PointMark` and `RuleMark` (gridlines) are already proven in this exact file (the shipped
  sparkline already used `Chart`/`LineMark`/`PointMark`); reusing them, plus the very standard
  `chartXScale`/`chartYScale`/`chartXAxis(.hidden)` modifiers, kept every new line of drawing code
  on APIs this codebase (or Charts' own well-documented surface) already proves compile. The one
  piece Charts has no clean API for — a stroke-only, background-filled "hollow ring" mark — is
  drawn as a plain SwiftUI `Circle` overlay instead of `chartOverlay`/`proxy.position(forX:/forY:)`
  (an API I could not verify against this SDK without a local Xcode): with `chartXScale`/
  `chartYScale` set to a **tight** domain (no Swift Charts auto-padding), the last point always
  lands exactly at the trailing edge, so the ring's position is `.overlay(alignment: .trailing)`
  plus a `y`-offset from the same `yDomain` fraction the chart itself plots from — arithmetic, not
  a read-back of Charts' own coordinate space.
- **`CourseSparklineModel` grows an `overall` property instead of a new model class.** UX-SPARK-2
  asks to "reuse UX-SPARK's shared model or cache pattern." `GradeTrend.compute` already returns
  both `perCourse` (what `CourseSparklineModel.series` used) **and** `ranges` (what Insights'
  "Performance trend" reads) from one call; `ranges[.term]?.points` is exactly the Dashboard hero's
  overall series, so caching it alongside `series` costs nothing extra — zero duplicate
  `GradeTrend.compute` calls, one `.task(id:)` per screen (`DashboardView` gets its own model
  instance, loaded the same way `CoursesScreen`'s already is).
- **D15 fixed entirely in the render layer, not `PriorityScore.swift`.** The defect's "likely
  source" hints at `PriorityScore.swift:225-229`, but `PriorityScore.Factor`/`ReasonPart` carry
  only a `Double`/`Int` hour count — turning that into a calendar day/weekday needs the absolute
  `dueAt` and a `Calendar`, neither of which belongs in TallyCore's pure scoring/ranking code (and
  `NextUpItem.dueAt` is already available at the one call site, `DashboardView`'s `NextUpSection`).
  `DashboardText.reason` grew an optional `dueAt`/`calendar` parameter (default `nil`/
  `.autoupdatingCurrent`, so every existing caller — including `RendererGoldenTests`' golden for
  "Due in 581h" — is untouched) and, 48 h+ out, reuses `L10n.Courses.dueAtTime`/`dueDay` (the exact
  keys `ScreenFormatter.dueText` already shows for Courses/To-Do) rather than adding a new key.
  `PriorityScore.swift` is unmodified; recorded as a deliberate deviation from the brief's file
  hint (rule 8: trust the code, cite `path:line`, continue).
- **Hero two-zone layout reuses `TallyReflowStack`/`TallyReflowSpacer`, not a bespoke AX branch.**
  The brief's literal text only requires the two-zone HStack; nothing in UX-SPARK-2 spells out AX5
  behaviour for the hero. FP-1/FP-2/FP-6's binding lesson ("keep FP-2's AX5 reflow") and the owner's
  AX5 bar (no overlaps/clips) argue for the same stacked-at-AX treatment every other two-part row
  on these screens already uses, so both heroes (Dashboard, Course Detail) get it too, even though
  the Courses-card section is the only one the spec calls out explicitly.
- **One new design token, `TallyColor.warning`.** D09 and D21 both trace to the same `.orange`
  family; a single Any #8A5300 (~6.3:1 on white) / Dark #FFB454 (~11.4:1 on `bg.canvas`'s dark
  value) token covers the text/icon use (D09) and, with `.opacity(0.16)` at the call site (the same
  pattern the file already used for the literal it replaces), the wash background (D21) — D21 is a
  shape/token defect, not a contrast one, so no second "fill" token was needed.
- **D25 fixed at the four tab call sites in `HomeShellView.swift`, not inside `SubscriptionLockViews.swift`.**
  `SubscriptionLock` replaces its content wholesale when locked, so whatever `.navigationTitle` the
  screen sets internally disappears with it. Setting it again just outside the modifier means the
  screen's own title (identical text) still wins unlocked, and is the only one left when locked.
  Calendar's own title is the live month, which needs data the locked state may not have projected;
  its outer fallback is the plain tab title (`L10n.Calendar.tabTitle()`), the same text Calendar
  shows before any data exists anyway.
- **No TallyCore changes** → no TallyCore test changes. All new tests are hosted
  (`apps/TallyiOS/TallyAppTests`) or UI (`apps/TallyiOS/TallyUITests`).
- **No string changes.** D15 reuses existing, frozen keys. Strings pending owner approval: **none**.
- **Regression tests: UX-SPARK-2's own "Tests (lean)" section only.** D08/D09/D13/D15/D21/D25 are
  all S2/S3 (pmo-ux-common.md only requires a regression check "for each S1 you fix"), so test
  effort stayed on what UX-SPARK-2 itself asks for.
