## Iteration 1 — local implementation, verified with Python self-tests and checkers only

**Item 1 — `StoreScreenshotUITests.swift` (new, `apps/TallyiOS/TallyUITests/`).** Eight scenes, one
capture each, at rest (pmo-ux-common.md's "captures only at rest"), on the flagship persona /
Sample Data: Dashboard (`dashboard.hero.averageOfCourses` + `dashboard.sparkline`), Courses
(`course.card`), Course detail with the Grades segment (`courseDetail.hero` /
`courseDetail.segment.grades`), the What-If sheet (`courseDetail.whatIf` / `whatif.projected`),
To-Do (`todo.row.*` prefix), Calendar (`calendar.day`), Insights (`chart.trend`), and parent mode
(`family.sample.viewAsParent` / `family.switcher`). Gated like the tour: every method skips in
`setUpWithError` unless `TALLY_STORE_SHOTS` is set (`TEST_RUNNER_TALLY_STORE_SHOTS` from the new
workflow). Appearance and language read `STORE_SHOTS_APPEARANCE` / `STORE_SHOTS_LANGUAGE`, set the
same way `AuditTourUITests` reads `AUDIT_APPEARANCE` / `AUDIT_LANGUAGE` (the workflow sets the
simulator's own appearance with `simctl ui ... appearance` before `xcodebuild test`, and
`currentLocaleArguments` is overridden the same way). Unlike the tour, every assertion is a hard
`XCTAssertTrue` (`continueAfterFailure` stays `TallyUITestCase`'s default `false`): these are the
real Store-bound captures, so missing scene content must fail loudly, not silently capture a blank
screen.

**Decision — scene 8 is parent mode, not a composited widget render.** The Home Screen is not
reachable in XCUITest. The brief allows an honest, composed widget render instead, but
`WidgetFamilyRenderTests` (TallyAppTests, M3-D's own file, outside this package's ownership)
doesn't have every combination this pipeline needs today — its hosted `snapshot` test covers
en-only, light/dark; its `spanishSnapshot` test covers es-only, light-only (no dark+es anywhere).
Closing that gap means editing a file another work package owns. The brief's own fallback applies:
"otherwise use parent mode" — real, synthetic-data app UI, already proven reachable in both
languages by `AuditTourUITests.testN_sampleDataAndParentMode` and `ReviewPathUITests`'s walk. No
app UI changes, no new strings, in either path.

**Item 2 — `scripts/release/screenshots.py` (new).** Pure Python + Pillow.
- `flatten_to_rgb`: composites any alpha channel onto white, otherwise a plain RGB convert. Only
  ever changes the alpha channel — never recolours or redraws app content (the brief's "nothing
  synthetic").
- `process_raw(raw_dir, out_dir)`: walks `store-shots-<light|dark>-<en|es>` leg directories (the
  workflow's own per-leg artifact names), flattens + asserts each of the 8 scenes at exactly
  1320x2868, writes the passing ones as `NN-<scene>-<mode>-<language>.png`, and writes
  `manifest.json` (scene, size, mode, language, SHA-256, whether the raw capture had alpha). A
  missing, unreadable or wrong-sized raw capture is recorded in `errors`/`missing` and left out of
  `images` — nothing passes by being missing, the same rule `check_release.py`'s own checks use.
- `build_contact_sheets(final_dir, out_dir)`: one `owner-sheet-<language>.jpg` per language, a
  portrait grid (light | dark per scene row), split into `-1`/`-2`/... parts under 4000 px tall,
  each stepped down in JPEG quality until under 1.5 MB.
- `--self-test`: flatten (alpha composited onto white, opaque pixels unchanged), `process_raw`
  (one complete leg, one leg missing a scene, one leg with a wrong-sized image, one leg entirely
  absent — every outcome shows up in the manifest), `build_contact_sheets` (splitting under a tight
  height cap; a byte cap tight enough to force the quality floor still writes a file).
  **Verified: `python3 scripts/release/screenshots.py --self-test` passes locally** (this host has
  Python 3.12 + Pillow 12.3.0, no Xcode needed for this script).

**Platform constraint (verified, not assumed): a brand-new `workflow_dispatch` workflow cannot be
dispatched until it exists on the repository's default branch.** Tried both ways:
```
$ gh workflow run "Store screenshots" --ref mvp/screenshots
could not find any workflows named Store screenshots
$ gh api --method POST /repos/rahart1362/Tally/actions/workflows/store-screenshots.yml/dispatches -f ref=mvp/screenshots

```
`gh workflow list --all` confirms `store-screenshots.yml` is absent while `Audit tour`/`Release
gate`/`CI` (already on `main` from earlier PRs) are `active`. This is a documented GitHub Actions
limitation (workflow_dispatch triggers are indexed only from the default branch), not a bug in the
new file. It means the brief's "2 screenshot dispatches (the tour or your gated job)" budget line
cannot be exercised standalone before this PR merges — unlike the Audit tour, which arrived on
`main` in a prior PR (#41) before any work package dispatched it.

**Adapted plan**: `release-gate.yml` (already registered on `main`) now has a `store-screenshots`
job that calls `./.github/workflows/store-screenshots.yml` with `uses:` — a reusable-workflow
relative-path reference, which GitHub resolves from the SAME ref/commit that triggered the run,
not from the default branch (a different rule from top-level `workflow_dispatch` registration).
So dispatching "Release gate" on this branch should exercise the new capture + post-process +
`REL.store.screenshots` pipeline for real, even though `store-screenshots.yml` itself stays
undispatchable standalone until the PR merges. This folds the screenshot pipeline's own iteration
into the release-gate budget instead of a separate one — recorded here, and in the report's open
items, rather than guessed at silently.
