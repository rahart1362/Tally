## Item 1 — SubscriptionEngineTests.launchRecordFirst (ASan race)

Confirmed against `SubscriptionEngine.swift`: `start()` is non-async internally — it calls
`enqueue(.launch)` and returns without awaiting the task. `verify()`/`foreground()`/`purchase()` all
go through `enqueue(reason).value`, which *does* await full completion. So `start()` is the only
entry point that returns before its verification's effects (including the `source.currentFacts()`
call that increments `reads`) have definitely run. In `launchRecordFirst`, the `F.eventually` only
waited for the gate to reach `.entitled` (set by the record-first `apply()`, which runs *before*
`currentFacts()` in `run(.launch)`), so the immediately-following `#expect(reads == 1)` could read 0
if the task hadn't reached the StoreKit call yet — matches the reported symptom exactly (0 reads, no
ASan report: a benign scheduling race, not a memory bug).

Fix: `apps/TallyiOS/TallyAppTests/SubscriptionEngineTests.swift:33` — added
`#expect(await F.eventually { rig.source.reads >= 1 })` before the existing `reads == 1` check.

Searched the rest of the suite (20 tests) for the same pattern (a plain `#expect` on a count another
task increments, right after a non-blocking trigger). Every other entry point in this file
(`foreground()`, `purchase()`, `accountAttached()`, `.started()`'s `settle()`) awaits the queued
verification or runs its side effects inline, so none race. **No other occurrences found.**
